## Context

本项目是一个单门店、多排练房的演示系统，当前代码库尚未建立业务实现。需求规格见本 change 下的 `specs/`；设计需要支持顾客自助预约、老板后台管理、线下会员卡和本地演示。

## Goals / Non-Goals

**Goals:**

- 用 React 构建中文响应式顾客端和老板后台。
- 用 Go 提供认证、会员、预约、库存、通知和管理 API。
- 用 SQLite 保存演示数据，并保证房间和设备预约冲突检查的原子性。
- 让开发阶段前后端可分开运行，演示阶段由 Go 提供打包后的 React 静态文件和 API。
- 让所有核心规则可测试、可审计，并方便准备软著演示材料。

**Non-Goals:**

- 不接入微信支付、支付宝支付或在线退款。
- 不实现多门店、员工权限、独立 App、乐队成员共享账号或真实商业化部署能力。
- 不把公共设备按租借价格计费；v1 中设备借用不额外收费。

## Decisions

### 1. Monorepo with separated frontend and backend

项目采用单仓库结构，前端和后端分目录管理。React 负责页面状态、表单、日历和响应式布局；Go 负责所有业务规则和数据访问。预约资格、会员消耗、时间冲突和设备库存不能只在前端判断。

开发时前端开发服务器和 Go API 分开运行；构建演示版本时，React 生成静态资源，由 Go 使用嵌入或静态文件服务统一提供，访问一个本地地址即可完成演示。

替代方案：使用 Node.js 全栈可以减少语言数量，但本项目已选择 Go 作为后端学习目标，因此不采用。

### 2. SQLite with repository/service separation

SQLite 作为本地数据库，数据库文件保存于项目数据目录。后端分为 HTTP/API、业务服务和数据访问层，避免把预约规则直接写进路由处理器，便于测试和未来迁移到 PostgreSQL。

替代方案：MySQL 或 PostgreSQL 更适合高并发生产系统，但需要独立服务和更多配置，不符合单门店演示项目的部署目标。

### 3. Resource intervals include cleaning time

预约记录保存实际排练开始和结束时间，同时计算资源占用结束时间 = 排练结束时间 + 30 分钟。房间和公共设备冲突都基于资源占用区间判断；清场时间不产生费用，v1 也不计算房间或设备租金。

时间统一按半小时对齐，预约时长限制为 0.5 至 3 小时。营业时间和特殊闭店规则由排程服务统一判断。

### 4. Transactional booking creation

创建预约时，后端在一个数据库事务中完成：验证登录和会员资格、检查用户未来预约、检查房间区间、检查公共设备库存、扣减次数卡（如适用）以及写入预约和通知。任何检查失败都回滚，避免两个同时提交的请求超卖同一房间或设备。

月卡优先于次数卡；次数卡在预约成功时扣减，取消后恢复。老板可以修改或取消预约并覆盖限制，但 v1 不提供老板主动新建预约入口。

### 5. Explicit status model and scheduled jobs

预约使用明确状态，例如 `confirmed`、`cancelled`、`completed`、`no_show`。定时任务负责处理预约完成、月卡到期提醒和其他基于时间的状态更新。定时任务需要可重复执行而不重复扣次数或发送重复业务结果。

### 6. Email as an adapter

邮件发送通过后端通知服务抽象，开发阶段使用测试邮箱配置，正式邮件服务只通过环境变量替换配置。预约状态更新先写入数据库，再异步或可靠地尝试发送邮件；发送失败不能回滚已成功的预约，失败记录进入后台供老板查看。

### 7. Role-based API boundary

API 明确区分顾客和老板权限。顾客只能读取和修改自己的资料、会员展示、预约、通知和反馈；老板才能管理房间、设备、会员、内容、统计、导出和操作日志。密码只保存安全摘要，邮件验证、密码重置和会话令牌使用一次性或有时效的凭证。

### 8. Demo-first seed data and packaging

项目提供可重复执行的演示数据初始化流程，包含示例房间、固定设备、公共设备、会员卡、顾客和不同状态预约。演示文档记录老板账号、顾客账号、启动方式和典型演示流程；真实密码和邮件密钥不提交到仓库。

## Risks / Trade-offs

- [Risk] SQLite 文件型数据库不适合未来高并发多门店业务 → 通过数据访问层隔离 SQLite，并把 PostgreSQL 迁移列为后续版本。
- [Risk] 定时任务未运行会延迟完成状态或会员提醒 → 后台每次读取相关数据时也执行安全的状态补偿检查，并在演示启动时运行一次任务。
- [Risk] 邮件服务配置错误影响通知 → 预约状态不依赖邮件成功；后台记录发送失败，开发环境提供测试邮箱配置。
- [Risk] 预约规则边界复杂，容易出现重复预约 → 所有规则集中在后端服务，并用冲突、取消、次数恢复和并发提交测试覆盖。
- [Risk] 中文文档在不同终端出现编码问题 → 统一使用 UTF-8，并在构建和演示环境中验证中文页面和 Markdown 文件。

## Migration Plan

这是新项目，没有旧数据迁移。初始化时创建 SQLite 表和演示数据；升级版本通过版本化数据库迁移执行。若演示版本出现问题，可停止 Go 进程并恢复上一份 `bandroom.db` 备份，代码和规格文件不受影响。
